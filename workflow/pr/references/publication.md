# Authorized PR publication

Read only when opening/updating a PR is requested and permitted. Use the target's host tooling and policy; GitHub examples assume authenticated `gh` and Git, not a required agent runtime.

1. Verify repository identity/access read-only, branch/base/target, existing PR and current remote head/body/state. Use discovered compatible `implementation-preflight` before authorized branch/commit preparation; it must preserve protected work and honor target branch/PR policy. Missing capability blocks preparation, not drafting. An already prepared correct branch needs inspection, not forced recreation. Never stage unrelated work, force-push, rebase, reset or resolve ambiguous ownership as a reporting side effect.
2. Reconcile intended published scope with the inspected report. Commit/stage/push only the exact approved branch/files when those effects are authorized. Dirty or local-only evidence must be labeled and cannot be represented as remote PR content. Preserve the reviewed fingerprint; content-equivalent commits need recorded equivalence, and state-sensitive checks need renewal by their owner. Changed content invalidates dependent checks/review/report claims before publication. An allowed draft PR may expose blocked work honestly; it never removes its acceptance blockers.
3. Recheck authority, disclosure, target and freshness immediately before sending. Honor the entry's `Closes #X` versus `Refs #X` rule and target completion, draft/status and release-label policy. Keep implementation issues open until project completion permits closure; opening a PR does not close them. For updates, preserve unrelated user-authored content; propose a scoped patch or ask if body ownership is unclear. Report-only requests perform zero remote writes.
4. Open/update only the approved PR. For GitHub, a prepared body file can be passed to `gh pr create --base <target> --head <branch> --title <title> --body-file <report>` or `gh pr edit <PR> --body-file <report>`. These examples grant no authority; inspect the existing PR before choosing create versus update. Apply only authorized metadata deltas.
5. Read back URL, repository, head/base, draft/state, title/body and any changed metadata. Compare the actual remote head and report against the intended state and evidence. A push is not a PR, and a successful command without read-back is not verified publication. After a timeout/partial failure, inspect actual remote state before retrying; return applied/unknown/failed effects separately. A clean rerun with matching body/state is a no-op.

**Complete when:** the authorized action and actual read-back match, or a precise partial/blocked outcome preserves the report and uncertain operations. Return to the caller; no automatic merge, closure, deployment, release or installation follows.
