# Specification publication

Read completely when tracker specification publication or reconciliation is requested. This procedure owns publication intent, fidelity and role/readiness outcomes, not the tracker's native graph algorithm.

## 1. Inspect destination and exact authority

Read target tracker/title/label policies and live mappings; verify read access, inspect existing spec identity and search relevant open/closed matches before creating. A failed search is unknown, not proof of absence. Reuse the matching authoritative spec; ambiguous matches require disambiguation. Resolve create/update and mapped-role authority from the selected command, agreed scope and target project agreement. Configured `/write-spec` selects publication of the agent-authored specification without a separate approval of routine wording. Credentials or behavioral agreement alone are not publication authority; project restrictions still apply. Ask only about genuinely missing permission or new consequential effects, not a second full-text review.

For GitHub, discover the actual `setup-project` package root through runtime/project metadata and read its complete `references/native-tracker.md` library entry directly, without the setup entry or label audit. Record source identity and check semantic compatibility; a missing/older incompatible library blocks this route without installation. It must support approved mapped spec/work-ticket roles, separate readiness, preserved unrelated state and native identity/pagination/read-back for any affected relationships. Other trackers need a project-approved native procedure. Missing permissions, mappings or required native capabilities block persistence, not drafting. Use the library if inspecting affected native graphs; preserve existing relationships and create no children or blockers as part of spec writing. No prose substitute for an unavailable requested native feature without explicit agreement.

**Done:** destination/existing identity, title and role mappings, deciding evidence and exact approved delta are known.

## 2. Publish the authorized delta

1. Follow the target's title convention; classify by purpose and mapped metadata, never title parsing.
2. Apply the mapped **specification role**, not the mapped **implementation-step role**. They are mutually exclusive. A conflicting role needs exact removal authority before correction. Preserve unrelated labels and relationships; assess other classifications independently. Creating/changing the label vocabulary requires separate approval.
3. Assess the next responsible actor independently of publication and scheduling. Apply the target's mapped agent-ready label when approved behavior and material shared design decisions support an actionable agent-suitable next action; apply the mapped human-ready label when the defined next action requires a human decision or capability. Represent unresolved scope and missing technical evidence explicitly; do not infer implementation readiness from publication. A human decision can be the next action without making the draft implementation-ready.
4. Include the justified readiness assignment alongside the spec role in authorized publication, using approved target mappings. Reuse task/project authority for routine classification without redundant confirmation; missing assignment authority blocks that effect. Native blockers alone neither suppress readiness nor select human readiness. An actionable parent spec is ready for coordination of eligible children, not duplicate parent implementation. Ready labels grant no dispatch authority, imply no accepted integration and never bypass native blocker/completion checks. Apply only authorized additions/removals; if a stale assignment cannot be corrected, report the contradiction and block reliance on it.
5. Write only content faithful to the agreed outcome and the authorized role/readiness delta. For an existing issue, preserve history, unrelated body sections, labels, parentage and blocker edges. Publication of a labeled draft is valid when specifically authorized; it stays draft and is not implementation-ready.

**Done:** each attempted effect and known/unknown result is recorded; no decomposition or implementation has begun.

## 3. Read back and compare

Read persisted identity, title, body/agreement pointer and revision, mapped spec role, absence of work-ticket role, independently assessed classifications/readiness and preservation of unrelated state. Compare actual values with the approved delta, not only command exit status.

After timeout or partial failure, inspect actual state before retrying. Never blindly recreate: uncertain identity could already exist. Failed reads or mismatches remain partial/unknown publication; report successful effects separately from failed/uncertain ones. Corrective operations need their own authority if outside the approved delta.

**Done:** matching read-back establishes publication; any unknown/mismatch is an explicit blocker. Return publication and readiness separately to the entry point, including evidence, operation states and smallest next action. Stop before ticket creation.
