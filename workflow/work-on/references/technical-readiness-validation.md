# Technical-readiness route validation

Read when changing or validating [the compatibility route](technical-readiness.md). Technical-analysis procedure and new routing cases now belong to discovered `analyze` and its package-local validation.

1. Follow [entry validation](validation.md#reproducible-static-checks) for rendered Markdown, frontmatter, links, isolated package copying and diff hygiene.
2. Inspect discovery through a non-sibling catalog or explicit approved source. Read complete Analyze entry/references, pin source identity and verify the required capabilities in [the adapter](technical-readiness.md).
3. Walk an actionable brief through the adapter: envelope to Analyze, inspected brief/recommendation back, lead method decision and separate build gate, then shipped ticketing only when useful or direct build. Standalone Analyze stops before this continuation.
4. Supply complete current analysis: consume its deciding-source support without automatic rerun. With changed caller/dirty code, refresh only dependent findings. Missing/incompatible/ambiguous Analyze blocks new analysis, not equivalent current evidence or unrelated inspection.
5. Exercise a missing method: the brief may be supported while method execution remains unavailable. Neither a recommendation nor closed prerequisite issue establishes ready-to-build/accepted delivery.
6. Verify entry, README and install guidance declare the new required companion for this route. The broad Work On entry, multi-ticket ownership, delivery gates and root budgets remain unchanged until their separate cutover.

These authored checks do not establish agent behavior. Record actual static checks, fixture tests, direct walkthroughs and absent independent review separately in repository evidence. No installation, model call, tracker mutation or delegation is needed to inspect the route.
