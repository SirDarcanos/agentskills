# Integrated verification

Read completely when implementation is integrated and entry selects acceptance verification, or affected checks need refreshing after a change. This internal Work On procedure owns evidence sufficiency, not integration, independent review, repairs or final acceptance. Consume current agreement, actual scope and raw checks from conversation or the target's existing evidence home. No new ledger or durable report is required for ordinary same-session verification. For changes or validation, read [verification validation](verification-validation.md).

## 1. Establish the state actually being verified

Consume the approved agreement revision, acceptance IDs, technical risk/check plan, implementation returns, baseline evidence, authority and protected scope. Read the actual integrated files/diff, relevant callers and raw check results. Compare behavior with the agreement rather than treating an implementer's “done” as proof. Confirm each claimed delivery is present in the target state; an unintegrated worker branch or its local green run is not integrated evidence. Direct building may already be in the target worktree; record that fact without requiring a merge or integration branch.

Identify branch/worktree, resolved base/HEAD, included committed/staged/unstaged/untracked changes and supporting inputs, protected exclusions and fingerprints. Discover the compatible `review-delivery` scope contract when needed for its detailed snapshot format; use that maintained format rather than inventing a second schema or invoking review. Record missing capability as an affected blocker. Non-Git work uses the contract's before/after manifest.

Freeze scoped writes/integration or use an authorized immutable snapshot before checks. Record the owner and verify the snapshot contains dirty files and material supporting inputs. Check agreement, environment/configuration and snapshot freshness again when consuming retained results. An unavailable historical baseline is unknown, not a successful baseline. Preserve unrelated work and confidential contents under the target's retention/disclosure rules.

**Complete when:** agreement, authority, integrated scope and check inputs are inspectable and pinned; every delivery claim has an inspected disposition, and missing material state/input evidence is blocked.

## 2. Map acceptance and material risks to checks

Inspect existing assertions, fixtures and documented commands for the affected behavior. Reuse the technical plan where current; refine routine check choices from actual integration evidence. Build a compact criterion/risk mapping in the existing record:

| Item | Record |
| --- | --- |
| Obligation | Acceptance ID or material failure mode, expected observable behavior and relevant source location |
| Coverage | Existing assertion/inspection and what it proves; a gap or needed extension with its distinct failure mode |
| Check | Applicable discovered command or bounded inspection, required environment/authority and expected result |
| Evidence | Baseline and integrated-state references, actual result/raw evidence pointer, limitations and criterion disposition |

A passing unrelated suite leaves the affected obligation unverified. A test name, count, coverage percentage or authored scenario establishes no behavioral evidence. Run applicable discovered checks under current authority; add/extend checks only for meaningful gaps, not a quota. Follow binding target policy and seek approval for a policy exception rather than silently weakening it.

Assess relevant failure paths explicitly: access denial and sensitive-data disclosure; interrupted persistence and recovery; destructive operations and protected data; important domain invariants and boundaries. Exercise them safely with authorized fixtures where sufficient. Record why a category is inapplicable, or why existing coverage suffices. A synthetic check supports only its modeled conditions; it cannot replace a required live/environment-specific check. Sensitive or destructive execution, installation, spending and new disclosure retain their separate approval gates.

For regression claims, inspect assertions and the observed failure cause. Prefer an existing red-before-green result, safe baseline comparison or bounded fault demonstration when useful and authorized. A check failing for a missing dependency does not show sensitivity to the intended bug. If sensitivity is uncertain, say so and assess whether that uncertainty leaves a material gap; verification does not impose universal mutation testing or TDD.

**Complete when:** every acceptance criterion and material risk has relevant coverage/check evidence or a named gap; additions have distinct failure-mode rationale, and relevant failure paths are covered or explicitly blocked.

## 3. Execute and classify evidence

Run the selected safe checks against the pinned integrated state. Record exact command/inspection, environment, exit/result, relevant raw output location and state checked. Preserve failures and partial runs. Local implementer evidence may be reused only after inspecting its raw results and demonstrating equivalence of all relevant content and supporting inputs; rerun integration/state-sensitive checks. Model agreement or a success summary is not a substitute.

Classify each observation without erasing its history:

| Observation | Required treatment |
| --- | --- |
| Current relevant pass | State precisely which behavior/risk it supports and its limitations. |
| Baseline failure | Establish comparable baseline state, environment and failure cause from actual evidence. Keep its impact explicit; “pre-existing” alone is not a waiver of acceptance. |
| New regression | A previously passing comparable baseline now fails for an affected behavior. Record cause/evidence and block the material obligation. |
| Failure of unknown origin | Baseline absent/noncomparable or cause uncertain: retain failed status and uncertainty; do not guess baseline versus regression. |
| Unavailable/not-run | Name missing tool, permission, environment or input, affected obligation and next action. Material gaps block immediately; no installation or performative retries. |
| Authored but unexecuted | Retain as a planned scenario, not an observed pass. |
| Uncertain sensitivity | Identify what was observed and which intended failure has not been demonstrated; resolve material uncertainty or block it. |
| Stale | State which scope/agreement/check input changed; preserve the old result for its old state and refresh affected evidence. |

At the end, repeat scoped candidate discovery and compare fingerprints, agreement and relevant check inputs. A new relevant path can invalidate coverage even when previously included files match. Drift blocks claims for the changed state; repin and rerun affected checks. Record any content-identical commit equivalence explicitly; rerun checks sensitive to branch, commit or integration state. Apply [completion's repair limits](completion.md#2-perform-bounded-repairs-and-inspect-results) to subsequent corrective work; this procedure reports findings rather than orchestrating repairs.

**Complete when:** each selected check has actual current evidence or an explicit failure/gap, baseline claims are supported, and the final freshness comparison accounts for changed inputs.

## 4. Return evidence sufficiency, not final acceptance

Inspect the actual mapping, artifacts and raw results against the agreement and material risks. For each obligation report **verified**, **unverified** (insufficient/uncertain evidence), or **blocked** (material failure or unavailable required evidence), with source/state, evidence and reason. Summarize implemented, deferred and excluded scope separately; a deferred commitment needs its owner's approval, not a verifier's relabeling.

Reject unsupported completion claims. Missing material evidence remains a blocker with a recommended bounded next action, or an explicit request to the agreement owner to change acceptance and accept the consequence. Until that change is approved and recorded in the authoritative agreement, the original obligation remains. Baseline defects can still block a required behavior; unrelated green checks cannot compensate.

Return the shared record with snapshot/freshness, criterion/risk mapping, commands/raw evidence, baseline versus regression dispositions, unavailable/unexecuted/stale checks, sensitivity limits, findings and documentation impact. Update the target's existing authoritative homes when verification changes their facts, or justify no change; use target policy rather than duplicating it here. Preserve approval and repair-history pointers.

Make actual files/diffs and raw evidence accessible to independent review under existing disclosure authority. Report absent/incomplete Standards/Spec review explicitly. Verification evidence is an input to review and the later completion gate, not a replacement for them. Select the next available responsibility through entry; if completion/repair or review capability is unavailable, return the affected blocker without inventing its procedure.

**Verification completion:** a revision-aware evidence-sufficiency handoff or preserved blocking result. This does not authorize final acceptance, ticket closure, merge, deployment or release.
