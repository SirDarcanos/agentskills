# Work on

## Invocation and prerequisites

Start only for an explicit user delivery request or bounded authorized assignment. The calling agent is the accountable **technical lead for one change**, including direct implementation. Discovery, library reads and investigation-only requests confer no fix authority. Whole-spec scheduling belongs to discovered compatible `work-on-spec`; do not reinterpret several tickets as one change or run a legacy dispatch fallback.

Locate applicable target instructions and the actual project agreement. Reuse meaningful existing guidance regardless of filenames or Setup origin. Check context/decision authority, requested effects and stage boundaries, safety, verification/review, documentation and evidence/continuation responsibilities. Read relevant context and directory/runtime restrictions, not every optional record. Missing or conflicting common guidance blocks dependent delivery with a specific reconciliation recommendation; do not invoke setup or invent policy. Missing tracker/model detail blocks only that capability. Common permissions, discovery, truthful evidence and persistence come from that agreement, not a universal Work On policy library.

Direct execution is the default. An explicit delivery request includes bounded independent reviews under [required-review authority](references/coordination.md#required-review-authority); optional implementation/exploration delegation still needs separate permission. Read [coordination](references/coordination.md) before launches or when active/uncertain workers exist. Assigned ticket leads request workers/reviews from the existing root, never create another pool. Read [optional model allocations](references/optional-models.md) only when a separately authorized assessment is relevant. These libraries do not invoke delivery.

For package changes or validation, read [validation](references/validation.md). [Contracts](references/contracts.md) retains compatibility targets for unmigrated library callers; it is not an ordinary-entry prerequisite.

## 1. Establish the bounded change and actual state

Identify the approved outcome, acceptance criteria or checkable brief, exclusions and exact permitted effects. Inspect actual artifacts, partial work and relevant callers/checks. In Git inspect branch/base/HEAD, PR state and staged/unstaged/relevant untracked work, modes and links; protect unrelated bytes, index state and history. Outside Git use a before/after manifest. Uncertain ownership blocks conflicting writes, not inspection.

Reusable-skill corrections target authoritative tracked package sources. A repository-local operating policy workaround is not a substitute for portable behavior. Installed copies remain unchanged unless separately approved.

For ticket work, discover the maintained tracker procedure and inspect paginated native parent/blocker observations and required accepted-integration evidence. For GitHub, use discovered `setup-project`'s documented tracker library without invoking setup. Failed access is unknown; closure or labels alone do not establish eligibility. A direct request needs no ticket hierarchy. Read [recovery](references/recovery.md) before writes when prior owners, operations, evidence or spent allowances are uncertain.

**Done:** scope, agreement, authority, protected work, actual progress and applicable eligibility have evidence or specific blockers.

## 2. Reuse deciding evidence and fill gaps

Compare supplied findings with current agreement, affected source/callers/checks/configuration/environment and dirty content identities. Inspect primary support and raw results. Reuse current complete evidence; phase changes or elapsed time alone do not justify another specialist run.

A ready bug ticket or conversation diagnosis supplies expected/actual behavior and impact, environment/reproduction/results, established cause/affected sources, bounded fix/exclusions/risks/dependencies and acceptance/regression/method advice. Consume it without reinvestigation. For missing diagnostic facts, discover compatible `investigate-bug` and supply only the gap within original fix authority. Diagnosis can return ticket-ready conversation evidence; tracker publication is a separate selected effect, not a fix prerequisite. Unresolved cause blocks the dependent fix.

Use [technical readiness](references/technical-readiness.md) only for missing technical decisions and [product agreement](references/product-agreement.md) only for unresolved commitments. Changed deciding inputs invalidate dependent claims; preserve unaffected and old-state evidence. Meanings/qualifying ADR changes retain the discovered domain owner's approval boundary. Several work units return to the overall-delivery boundary rather than being scheduled here.

**Done:** current agreement and technical evidence support one bounded implementation, or material gaps have owners and next actions.

## 3. Select and execute the method

Read [build](references/build.md) completely. The lead selects a compatible method from actual readiness, risks and binding target policy, without a maintainer method/seam questionnaire. Discover/read the selected method and relevant references; record source/revision or digest. Available names alone do not establish capability. `tdd`, `prototype`, `characterize`, `acceptance-first` and `build-and-check` own their distinctive loops.

Inspect each method return and raw artifacts/checks. Sequential methods retain baseline/experiment disposition, current evidence and any existing checkpoint/coordination state without restarting analysis for unchanged facts. Prototype learning and characterization protection are not production acceptance. Missing selected capability blocks that route, without installation or legacy substitution.

**Done:** safe preflight, implemented or preserved partial artifacts, local evidence and documentation disposition support the next gate.

## 4. Verify, review and repair

Read [verification](references/verification.md) completely. Map every acceptance criterion/material risk to current evidence, pin full delivered scope/supporting inputs and freeze writes. Reuse inspected raw checks only when relevant inputs are equivalent; rerun state-sensitive checks. Failed, unavailable or stale material evidence blocks acceptance immediately.

Discover compatible `review-delivery`, read its complete entry and applicable references, and obtain separate independent Standards and Spec contexts against the same pinned committed/dirty scope and raw checks. Preserve original reports; lead inspection or optional model agreement cannot substitute. The root launches reviews under conditional coordination; ticket workers request them. Missing capability/restriction yields implemented-but-unaccepted work.

Read [completion](references/completion.md) completely for findings, two-cycle bounded repair, renewed affected checks/review and distinct build/accept/report decisions. Preserve checkpoint/finding lineage and spent allowances across methods and resume. Exhaustion, substantive disagreement or unsafe authority stops affected correction with preserved evidence and a bounded reassessment recommendation.

**Done:** current verification and independent review support the delivery decision, or explicit unverified/blocked obligations remain.

## 5. Return delivery status and stop

Return implemented, verified, unverified, deferred and blocked scope; artifact/check/review pointers, documentation/changelog disposition, distinct gate decisions, actual branch/PR/issue state and next action. Same-session evidence may remain in conversation. User-selected persistence does not erase active owners, uncertain effects or spent allowances; preserve that safety state under project guidance without manufacturing a routine durable run report.

Ordinary delivery stops here, before PR preparation or publication, even when branch/commit/push is allowed. Offer PR work as a next stage. Only when the user selects it (including an explicit compound request), discover/read compatible `pr` and pass current evidence, original reviews, gates, impact baseline and exact effects. It owns PR reporting/publication, not another delivery run. An unavailable PR companion does not block delivery status. Keep issues open until target completion policy permits closing; no merge, installation, deployment or release is implied.

**Complete:** truthful delivery status, including an honest partial result when acceptance remains blocked; no automatic PR or handoff stage.
