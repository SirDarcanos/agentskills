# Build and Check

Own the implementation-first loop and current local evidence, not independent review or delivery acceptance. Use directly for matching requests or inline through a bounded authorized handoff. Read [validation](references/validation.md) when changing or validating this package.

## 1. Establish scope and checks

Read target instructions, the authoritative agreement/revision and acceptance references, exclusions, affected files/callers, existing coverage and supplied readiness evidence. Compare deciding sources, dirty work, tests, configuration and environment; reuse current evidence and investigate only material gaps. Ordinary request/context supplies these facts without a mandatory form.

Identify one owner, protected work, approved file/run effects, data/retention constraints and expected return. Plan-only authority returns an increment/check plan without writes. This method grants no installation, service startup, disclosure, spending, delegation, tracker mutation, merge or release authority.

Discover conditional companions through the runtime catalog or an explicit approved location, not sibling paths. Read complete entries and relevant references, record source/revision or digest and check semantic capabilities. Missing, ambiguous or incompatible helpers block their dependent route without installation or legacy fallback:

- Before Git writes, consume compatible `implementation-preflight` or inspect a current caller-supplied result for this scope/state. Outside Git retain a before/after manifest.
- Changed meanings or qualifying decisions use discovered `domain-modeling`; reading definitions alone needs no invocation.
- Delegation or correction of recorded acceptance findings consumes discovered `work-on`'s execution/repair library without invoking delivery. Retain root ownership, ledger, bounds and finding lineage; workers request additional work from the root. Ordinary direct development increments need no delivery companion.

Map each scoped acceptance/risk to an appropriate existing check or focused inspection, expected result, command/environment and finite run bound. Inspect assertions and relevant paths rather than relying on test names/counts. Reuse sufficient coverage; add or extend checks only for a real gap. No new-test quota, coverage target or mandatory unit suite applies. Binding project method/check policy still applies; selecting this method cannot waive it.

For documentation check affected facts, frontmatter, links/anchors and rendered structure; for configuration use its actual parser/schema or consumer check where available, including relevant safety settings. Code checks cover changed behavior and meaningful regression/failure paths. Record why focused inspection suffices when no executable check is appropriate. Material unavailable checks remain gaps, not green results. Run safe relevant baselines when useful to distinguish existing failures.

**Complete when:** scope, authority, ownership, deciding inputs and risk/check mapping are actionable, or affected blockers are recorded with protected work intact.

## 2. Implement one bounded increment, then check it

Select the smallest coherent increment with an observable result and a check that can finish now. Modify only its owned scope, then immediately run the mapped tests/validation or perform the focused inspection **before starting the next dependent increment**. Include non-code changes in this loop. Refactoring within scope is another checked increment; maintain agreed behavior and interfaces.

Inspect raw output, exit status and observable effects against expectations. Record changed artifacts, actual command/inspection, result and checked source/test/configuration/environment identities, including dirty content. A success summary or HEAD alone is insufficient. Preserve evidence for its original state.

A failed or materially unrun check stops dependent progress and its completion claim. Classify regression, pre-existing failure, harness/environment limitation or unresolved decision; preserve partial work and diagnose within authority. Repair the affected increment and rerun its checks before continuing, or return blocked with the smallest next action. Safe unrelated inspection may continue; do not accumulate unchecked dependent increments, weaken assertions or silently skip checks. Missing tools/permissions are blockers, not permission to install or substitute inadequate validation.

Ordinary implementation defects are development; corrective work on a recorded acceptance finding retains the shared checkpoint, lineage and spent repair budget across resume or method switches. Unknown permission or exhausted correction allowance stops the affected route. Changed product commitments, scope, meaningful risk/cost or authority return to their owner with evidence and a bounded recommendation.

After a pass, select the next increment within the same agreement. Rerun dependent checks after subsequent edits or changed callers/configuration/environment; retain unaffected current evidence. Update authoritative owned documentation/changelog under target policy or justify no change. If another method becomes appropriate, return the evidence and recommendation to the caller rather than recursively launching it.

**Complete when:** every implemented increment has current relevant local evidence, or failed/unrun/stale checks and preserved partial work explicitly block dependent progress.

## 3. Inspect and return local evidence

Inspect the actual diff/manifest against scope, instructions and protected bytes, index state, modes and link targets. Account for probes, test data and scratch; remove only authorized unchanged owned artifacts, preserving uncertain or interveningly changed work.

Return **complete**, **partial** or **blocked**, with:

- Agreement/revision, acceptance references, scope/exclusions, authority/owner, companion/preflight sources and branch/base/PR target or non-Git manifest.
- Increment order, changed artifacts, risk/check mapping, actual commands/inspections and observed results, baseline distinctions, checked identities and raw evidence pointers.
- Implemented versus verified, deferred and blocked scope; failed, not-run, stale or unavailable checks, uncertainty, documentation disposition and next action.
- Protected/retained/restored artifacts and shared finding/ledger state when applicable.

**Method completion:** bounded implementation has current local evidence, or a truthful partial/blocking return preserves work. Local passes do not establish independent review or final integrated acceptance. Stop at the caller handoff; this method does not open a PR or start another delivery phase.
