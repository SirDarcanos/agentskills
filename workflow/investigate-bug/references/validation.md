# Investigate Bug validation

Read the complete entry, README and affected conditional references before changes. This is an instruction package, not an executable diagnosis/readiness engine. Perform these checks from an independently copied package; this procedure needs no source checkout, development history or tracker for this collection.

## Package checks

1. Inspect frontmatter and routing: ordinary diagnosis and bounded handoffs are supported; investigation-only ends before repair, not at a mandatory ticket. Read the project's applicable agreement once; missing/conflicting guidance blocks dependent work without inventing policy or running setup.
2. Inspect Markdown structure, headings, tables and fences; follow every internal link and anchor. Copy the whole directory, including LICENSE, to a non-sibling temporary catalog and repeat. Companion discovery uses runtime/project guidance, never assumed sibling links. Inspect all reachable instructions, including this maintenance procedure, for accidental source-repository prerequisites.
3. Check finite diagnostic bounds, wrong-reason failures, complete diagnosis content, deciding-input reuse/invalidation and probe ownership/cleanup. Compare final scoped state with the original, preserving unrelated bytes, index state, modes, links and history. Review the diff for credentials, private data and nonportable paths.
4. Walk the cases below against actual instructions and, when authorized, a disposable target with supplied operating guidance and synthetic defective code. Record invocation, environment, commands/observations, before/after protected-work identities and actual returned evidence. For a runnable example, a fractional discount of `.10` applied to a subtotal of `100` should yield `90`; a synthetic implementation subtracting `.10` directly yields `99.9`. Use zero-discount and changed-caller controls to distinguish cause and stale applicability. Keep fixture code/probes isolated; do not ship a fix during diagnosis.
5. Record affected docs, actual commands/results and unrun branches under the target's evidence guidance. No installation, model assessment, delegation or live tracker mutation is required. Tracker exercises use explicitly disposable local fixtures unless live effects are separately authorized.

## Diagnosis and continuation walkthroughs

These are authored expected observations, not executed agent trials or proof of policy enforcement.

| Starting state | Required observable outcome |
| --- | --- |
| Confirmed symptom and established cause; no tracker credentials, Write Tickets or publication request | **Diagnosis complete — implementation-ready** in conversation with expected/actual behavior, impact, reproduction/environment, causal path, affected identities, bounded fix/check/method recommendation, exclusions/risks/dependencies and probe account. No tracker search, draft, persistence or downstream invocation. |
| Unrelated tracker outage; local deciding evidence available | Complete supported local diagnosis; no ticket capability blocker invented. If a tracker holds genuinely necessary deciding evidence, name that specific diagnostic gap instead. |
| Confirmed symptom but unresolved cause, or unconfirmed symptom | **Partial/blocked — investigation-only**, attempted observations, remaining hypotheses, missing confirmation/cause and smallest bounded diagnostic next action. No invented ready fix, mandatory ticket or automatic Work On recommendation. |
| Intermittent result or wrong-reason harness/permission failure | Record attempts/failures/successes and environment limits within bounds; a pass does not disprove intermittency and a harness error does not confirm the symptom. |
| Current complete evidence supplied | Compare source/callers/configuration, dirty identities and raw observations; reuse without automatic Analyze/reproduction. Changed caller/contract invalidates dependent claims only; unknown impact expands staleness honestly. |
| Owned probe cleanup encounters intervening unrelated edit | Preserve it; disclose remaining instrumentation and block ready handoff until safely accounted for. No stash/reset or cleanup of uncertain ownership. |
| Investigation-only suggests a useful next step | Recommend direct work for a bounded ready fix or ticket creation for important/larger tracked work; do not execute either. No missing issue URL or success label substitutes for diagnosis. |
| Explicit investigation-and-ticket; project permits scoped publication | Continue through discovered Write Tickets in this context without another command or duplicate wording approval. Inspect duplicates, actual artifact, authorized effects and read-back; return concise linked IDs, diagnostic readiness separately. |
| Ticket stage explicitly draft/local-only, or publication declined | Zero remote writes; label the actual draft/unpublished disposition without blocking an otherwise complete diagnosis or insisting on publication next. |
| Matching current issue or partial/unknown ticket creation | Preserve canonical identity and unrelated body/labels/edges; only exact authorized reconciliation and verified read-back. Inspect uncertain outcomes before retry, never create a duplicate or automatic closure. |
| Ticket stage requested but Write Tickets/access/read-back unavailable | Diagnosis status remains evidence-based; selected ticket stage is specifically blocked/partial with actual operations and next action. No fabricated ID, installation or automatic fix. |
| Explicit investigation-and-fix | Return complete current diagnosis and original approved effects to a compatible delivery lead without a ticket or second user command. Receiver checks freshness/build gate and fills only actual gaps; investigation itself performs no repair. Unresolved cause blocks fixing. |
| Mixed installation: delivery owner still requires a ticket or delegation exposes only old universal contract | Mark that continuation unavailable and preserve diagnosis. Do not pretend compatibility, weaken gates, manufacture a ticket, install replacements or block equivalent direct diagnosis. |

**Done:** applicable checks have actual results, artifact/protected-work disposition and explicit material gaps. Static inspection, authored fixture assertions and autonomous agent behavior are separate evidence categories; successful local checks do not certify live tracker APIs or a later delivered fix.
