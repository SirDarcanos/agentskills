# Domain-modeling handoff

Read during planning when setup finds established terms, existing domain records/context maps, or architectural decisions needing assessment. The maintained `domain-modeling` companion owns the procedures; this reference only connects it to setup's [documentation contract](documentation-contract.md).

## Procedure

1. Locate `domain-modeling` through runtime skill discovery and read its complete SKILL.md. Follow its handoff reference for inputs, modes, ownership, and outputs. Verify that the discovered package supports that contract; a same-named older installation is not automatically compatible. No literal Skill tool or separate agent is required.
2. Supply setup's target, inspected domain evidence, authoritative document mapping, confirmed decisions and sources, unresolved questions, operating authority/constraints, and exclusions. Request **plan-only** while setup gathers its approval plan. Incorporate the proposed domain deltas, pointer needs, and blockers into that single plan; no domain writes occur yet.
3. After approval, supply **approved** mode with the exact authorized files/sections and operations. Reuse confirmed answers; new decisions or changed scope return to setup before execution. Setup retains ownership of operating docs and entry-point integration.
4. Inspect the companion's results against the plan and actual files. Integrate returned read/update pointers only within the approved scope. Report omissions, mismatches, verification gaps, and blockers separately from completed work.

If the companion is missing, ambiguous, or incompatible, block the affected domain route and ask before installing or replacing anything. Do not substitute an older procedure or duplicate the specialist's instructions here. Independently approved operating-document work may proceed, but required domain work remains incomplete.

If inspection establishes that no domain records exist and no terms or architectural decisions need modeling, omit this route explicitly; the companion is not required merely to create an empty artifact. Uncertainty about a required domain change is a blocker, not an omission.

**Done:** domain work is either verified through the companion, explicitly unnecessary, or reported as deferred/blocked; setup owns no duplicate modeling procedure.
