# Work On Spec

Deliver or resume an explicitly requested specification across its tickets. The caller is the one overall technical lead: it reconciles native dependencies, assigns bounded changes to Work On ticket agents, reserves exclusive ownership, inspects returns, integrates serially and owns aggregate verification, review, repair and recovery.

Use `/work-on-spec <approved specification>` or an ordinary request for overall delivery. Reading or decomposing a specification grants no build authority. For one bounded change, use `work-on`; for investigation-only work, use `investigate-bug`.

## Installation and compatibility

After approving exact destination/collision scope, install or copy the complete package, including references, script and [MIT notice](LICENSE). Example commands, not executed by this workflow:

```sh
npx skills add SirDarcanos/agentskills --skill work-on-spec
npx skills add SirDarcanos/agentskills --skill work-on
npx skills add SirDarcanos/agentskills --skill review-delivery
npx skills add SirDarcanos/agentskills --skill pr
```

Start at [SKILL.md](SKILL.md). Discover companions through the runtime/project catalog or approved source location, not sibling directory paths. Read complete entries and relevant references, inspect semantic capabilities and record actual resolved sources/revisions. Stage a coherent repository release/source revision; names alone are not compatibility. Repository merge does not install or replace global copies.

Required for execution: meaningful target-project guidance, compatible Work On bounded returns/conditional coordination library, native tracker inspection, and separately authorized writable bounded ticket-agent runtime with exclusive ownership/isolation, finite lifecycle control and inspectable results. An inspect-only delegate is insufficient. Without that route, graph inspection/planning can finish with execution blocked; no silent direct whole-spec or legacy fallback. The root chooses and adjusts concurrency through Work On's conditional coordination library, with rolling scheduling rather than a universal worker count or fixed ticket batches. Actual resource constraints or explicit project/runtime restrictions can require serialization; local review must not become a barrier for unrelated eligible work. Existing consumer-policy limits require separately approved reconciliation, not automatic override. The root alone launches under the existing root assignment record; assigned local leads cannot recursively fan out.

Required for acceptance: applicable target checks and independent `review-delivery` with separate Standards/Spec contexts. Ordinary delivery returns integrated/per-ticket status before PR preparation/publication; `pr` is needed only when the user selects that stage. Same-session evidence can remain in conversation without a durable report or handoff. Active owners, uncertain effects and spent allowances still require safe accounting before interruption. Work On solely owns conditional coordination/verification/completion/local-recovery libraries; this package supplies whole-spec inputs and owns dispatch, cross-ticket obligations and overall recovery. Conditional Work On companions remain necessary for Git preflight, selected methods, missing analysis/product facts, ticket reconciliation and domain decisions. For GitHub graph inspection, discover the `setup-project` package root and read `references/native-tracker.md` directly, without its setup entry or label audit; missing/incompatible libraries block that route. Missing native access blocks graph-dependent eligibility rather than falling back to prose.

Optional `ask-*` calls require exact approved policy and a root allocation, never installation, substitution or an independent-review waiver. Availability is not permission. Missing approved permission means no autonomous calls; offline validation makes no calls.

## Results and validation

Return local versus integrated/aggregate evidence, waiting and blocked tickets, preserved artifacts, shared checkpoint/worker/model history, documentation disposition and distinct build/accept/report gates. A ready parent is a coordination input. Closed prerequisites, local green results or a staging branch cannot establish target-required accepted merge. Integration refreshes affected/cross-ticket checks and significant-change review. PR opening, maintainer acceptance, merge, deployment, release and installed migration remain separate.

Read [validation](references/validation.md) and [dispatch cases](references/dispatch-validation.md). Run the shipped offline fixture with Python 3 and Git; it uses disposable local repositories and synthetic graph/lifecycle/acceptance decisions, not a live tracker, delegation engine or autonomous agent trial. Fixture passes do not establish composed runtime/failure acceptance.

Procedures are reused from repository-owned Work On material under Nicola Mustone's MIT notice; no external skill bodies are imported. No mandatory integration branch, merger agent or new orchestration service is introduced.
