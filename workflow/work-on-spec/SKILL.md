# Work on spec

## Invocation and prerequisites

Start only for explicit overall specification delivery or its authorized continuation. The caller is the **one overall technical lead**; bounded ticket leads use `work-on`. Cross-ticket decisions, shared interfaces, scheduling, serial integration and whole-agreement accountability stay here. Reading or decomposing a spec grants no execution authority.

Locate target instructions and the meaningful project agreement. Reuse equivalent guidance for context/decision authority, requested effects/stages, safety, verification/review, documentation and evidence/continuation; read relevant directory/runtime restrictions and context, not every optional record. Missing/conflicting common guidance blocks dependent work with a specific reconciliation recommendation, not automatic setup. Conditional gaps block only their capability. The agreement owns common policy, including publication and persistence.

Discover compatible `work-on`, read its complete entry and record source/revision or digest. Resolve its documented operational references from that inspected entry, not guessed filenames or sibling installations. Consume only needed libraries without invoking single-change delivery: coordination before assignments or with active/uncertain workers; verification/completion for aggregate acceptance; local recovery on uncertain state; optional-model allocation only for a separately authorized assessment. Require bounded returns, root-owned launches, retained history and distinct local/integrated evidence. A legacy universal-contract-only companion blocks the affected route; no installation or fallback scheduler.

Multi-ticket execution requires authorized bounded writable Work On ticket assignments, exclusive isolation, lifecycle inspection and separately inspectable results. An inspect-only delegate cannot implement tickets. Without that capability/permission, return inspected graph/planning progress with execution blocked; do not silently substitute direct whole-spec building. Use coordination's lead-chosen concurrency with rolling scheduling rather than fixed ticket batches. Ticket leads request workers/reviews/model allocations from this root, never another pool. Required read-only review uses Work On's documented review authority; optional implementation delegation remains separately authorized.

For package changes or validation, read [validation](references/validation.md).

## 1. Establish agreement and actual progress

Pin approved spec/acceptance IDs, exclusions, intended tickets and exact permitted effects. Inspect actual artifacts, branches/worktrees, dirty/protected work, PR/acceptance/merge evidence and existing root assignment state. Reuse current supplied investigation/analysis, decisions and raw checks after comparing affected sources, callers, configuration and environment; refresh only missing/stale claims. Missing consequential intent returns to its owner; routine engineering stays with the lead. Discover specialists only for actual product, technical, ticketing or domain gaps.

Discover/read the maintained native tracker procedure; for GitHub discover the actual `setup-project` package root and read its complete `references/native-tracker.md` library entry directly, not its setup entry or label audit; check source identity and compatibility, blocking the route if missing/incompatible without installation. Read [recovery](references/recovery.md) before writes/launches when graph, owners, effects, evidence or spent history are uncertain. Same-session evidence may remain in conversation; a hypothetical next session creates no durable-storage prerequisite. Active/uncertain ownership, effects and spent allowances still require safe accounting.

**Done:** scope, authority, dependencies, protected state and actual progress have evidence or named blockers; root coordination state accounts for existing assignments.

## 2. Schedule and integrate bounded tickets

Read [dispatch](references/dispatch.md) completely for graph reconciliation, accepted-integration prerequisites, frontier/ownership reservations, bounded assignments, inspected returns and serial integration. Failed graph reads are unknown; labels or closure do not prove eligibility. Parent/subordinate specs are coordination inputs, not duplicate implementation tickets.

Before launches refresh prerequisites, active assignments/resources, ownership and base/interface assumptions. Reassess after relevant events without waiting for unrelated work or review. Supply scoped agreement, actual evidence, authority, root assignment reference and existing checkpoint history. Ticket leads choose methods and return implemented/verified/unverified/blocked scope, actual artifacts and raw checks. Cross-ticket decisions return here before dependent writes. Target PR/merge policy governs integration and unlocks; required publication is a separately selected stage, never implied by delivery.

**Done:** every requested ticket is eligible, waiting, active, integrated or blocked with inspected evidence and a next gate.

## 3. Verify and review the integrated agreement

Read [aggregate acceptance](references/aggregate.md) completely. Consume resolved Work On verification/completion as libraries with overall agreement, integrated snapshot, cross-ticket risks and final-integration checkpoint. Local ticket passes do not establish a whole-spec pass.

Obtain current integrated checks and independent Standards/Spec review through compatible `review-delivery`. This root launches reviewers within existing capacity; authorship and independence stay separate. Significant repairs renew affected evidence; moving findings across tickets/checkpoints never replenishes spent allowance. Missing material checks/review block acceptance, not honest partial reporting.

**Done:** every overall obligation and material finding has a fresh disposition or specific blocker, with original evidence and budget history preserved.

## 4. Return delivery status and stop

Use completion's separate build/accept/report decisions and documentation/tracker disposition. Return overall and per-ticket implemented/integrated, verified, unverified, approved deferred/excluded and blocked scope; frontier/assignment history, artifacts and protected state, existing checkpoint/model history, documentation/changelog disposition, actual branch/PR/issue/acceptance/merge state and next action. An honest partial report may complete while acceptance remains blocked. Keep issues open until target completion policy permits closing.

Ordinary delivery stops before PR preparation/publication. Offer that next stage without invoking it. Only a user-selected PR stage, including an explicit compound request, discovers/reads compatible `pr` and supplies current aggregate/ticket evidence, original reports, baseline, gates and exact effects; inspect its return/read-back. An unavailable unrequested PR companion or unrequested handoff/storage destination is not a delivery blocker. Same-session evidence can remain in context; protect active ownership, uncertain effects and spent history under coordination/recovery before interruption.

**Complete:** evidence-backed integrated/per-ticket status or preserved blockers; no automatic PR, handoff, merge, installation, deployment or release.
