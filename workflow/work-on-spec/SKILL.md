# Work on spec

## Invocation and shared ownership

Start only when the user requests overall specification delivery, including an authorized continuation of that delivery. Merely reading a spec, decomposing it, or investigating a bug grants no execution authority. The calling agent is the **one overall technical lead**; ticket agents use `work-on` for bounded changes. Cross-ticket decisions, shared interfaces, scheduling, integration and whole-agreement accountability stay here. Loading a skill launches nothing and grants no installation, spending, disclosure, tracker mutation, destructive operation, merge, deployment or release permission.

Before coordinating, discover `work-on` through the runtime/project catalog or an explicit approved source, read its complete entry and `references/contracts.md`, and record the resolved source/revision or digest. Confirm those required reads are complete before coordinating; use the contract's “Complete reads and reference resolution” procedure for incomplete output and companion/library paths, including tracker discovery. Consume that contract as a read-only library without invoking its single-change entry. It solely owns handoff/evidence fields, shared worker/repair/model limits and delivery gates. Require compatible bounded assignments, inline method/specialist use, root-owned launches, retained history and distinct local/integrated evidence. Ambiguous or missing companions block dependent routes, never trigger automatic installation or legacy fallback. Recheck compatibility on changed sources, authority or resume.

Multi-ticket execution requires an authorized runtime capable of bounded writable `work-on` ticket assignments, exclusive isolation, lifecycle inspection and separately inspectable results. An inspect-only delegate cannot implement tickets. Without that capability/permission, inspect the graph and return a plan or preserved blocker; do not silently substitute an overall direct build or create another orchestration service. With fewer available slots, serialize eligible ticket assignments and independent review axes under the discovered shared ceiling. Ticket leads request additional workers/review/model allocations from this root rather than launching recursively.

For package changes or validation, read [validation](references/validation.md).

## 1. Inspect the agreement, context and actual progress

Read target instructions and their project/workflow/authority, documentation, relevant domain/ADR and tracker/label pointers. Pin the approved spec and acceptance IDs, exclusions, intended tickets and exact permitted effects. Inspect actual branches/worktrees, dirty artifacts, protected work, existing PR/acceptance/merge evidence and retained root ledger. Missing consequential intent goes to its owner; routine engineering choices stay with the lead.

Reuse current ticket investigation/analysis and local decisions after inspecting cited sources/raw evidence and comparing deciding content, callers, configuration and environment. A new ticket/phase or elapsed time alone warrants no fresh investigation, analysis or optional model call. Refresh only dependent missing/stale claims; preserve unaffected decisions. Shared trade-offs return to this lead; product changes require agreement-owner approval. Discover `analyze`, `shape-work`, `write-spec`, `write-tickets` or the domain owner only for their actual gaps, through Work On's capability contract.

If owners, operations, graph, evidence or budget history are uncertain, read [recovery](references/recovery.md) before writes or launches. Multi-session work uses an approved durable evidence pointer, not a new committed state service.

**Done:** approved overall scope, authority, evidence/protected-state inventory and one root ledger are identified, or affected blockers are explicit.

## 2. Reconcile, schedule and integrate bounded tickets

Read [dispatch](references/dispatch.md) completely. It owns native graph reconciliation, prerequisite accepted-integration evidence, frontier and exclusive ownership reservations, bounded Work On assignments, inspected returns and serial lead integration. Discover the maintained tracker library via Work On's capability contract; for GitHub this is the discovered `setup-project` tracker reference, not setup invocation. Unknown graph reads block affected eligibility; titles, role/readiness labels and closed issues cannot substitute for native relationships or completion evidence.

Treat parent/subordinate specs as coordination inputs, not duplicate implementation units. Before each launch, refresh prerequisites, active slots, ownership and base/interface assumptions. Supply the shared envelope, local checkpoint and root-ledger pointer. Ticket agents choose methods locally and return implemented/verified/unverified/blocked scope and raw artifacts. Cross-ticket decisions need this lead's disposition before dependent writes. No mandatory integration branch or merger agent; actual target PR/merge policy governs integration and dependent unlocks.

**Done:** every requested ticket has a traceable eligible/waiting/active/integrated/blocked disposition, inspected progress or preserved artifacts, and an evidence-backed next gate.

## 3. Verify and review the overall delivered agreement

Read [aggregate acceptance](references/aggregate.md) completely after integration and when evidence changes. Consume resolved Work On verification/completion as libraries, supplying the overall agreement, integrated snapshot, cross-ticket risks and final integration checkpoint. They retain their procedure ownership; this package owns the additional aggregate obligations and decision scope.

Local ticket passes do not establish a whole-spec pass. Obtain current integrated criterion/risk evidence and independent Standards/Spec review through discovered `review-delivery`. This root launches read-only reviewers within the same capacity pool; review authorship and independence remain separate. Significant repairs renew affected checks/review; moving a finding across tickets or checkpoints cannot replenish spent allowance. Missing material checks/review block acceptance, not honest partial reporting.

**Done:** all overall obligations and cross-ticket findings have fresh dispositions, or named blockers with preserved evidence and unchanged budget history.

## 4. Return accountable delivery and authorized PR handoff

Use the resolved completion contract for distinct build/accept/report decisions, documentation and scoped tracker-readiness disposition; use discovered `pr` for plain-language reports or authorized opening/updating. Supply actual aggregate and ticket evidence, original axis reports, baseline, ledger and exact effect authority. Inspect returned reports/publication read-back. Keep issues open until target completion policy permits closure; a merge requires its own approval.

**Complete:** return overall and per-ticket implemented/integrated, verified, unverified, approved deferred/excluded and blocked scope; graph/frontier history, artifacts and protected state, root ledger/checkpoint/model history, documentation/changelog disposition, separate gates, actual acceptance/PR/merge state and concrete next action. A preserved blocked outcome is useful completion of reporting, not accepted delivery. No global installation or release is implied.
