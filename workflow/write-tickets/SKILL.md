# Write tickets

## Invocation, authority and companions

Use for ordinary matching requests or bounded authorized handoffs. Own cohesive decomposition, ticket publication/reconciliation and verified native relationship/role outcomes. Stop before scheduling, implementation, closure, merge or release. A configured `/write-tickets` request selects scoped ticket publication under project authority, not new consequential scope, arbitrary graph changes or unrelated effects. Explicit draft, local-only or review-only requests override writes.

Reuse the project's applicable instructions and agreement once per context, including relevant context/authority pointers and directory/runtime restrictions. Check meaningful decision/effect, safety, verification, documentation and continuation guidance, not Setup provenance or templates. Identify specific absent/conflicting guidance and recommend explicit reconciliation without starting setup or rewriting policy. Missing common guidance blocks dependent project work; missing tracker/model/domain detail blocks only that capability.

Accept agreed conversation/plans/specs or bounded bug investigations, including explicit handoffs. Keep evidence in context or the user-selected destination; no mandatory form, delivery run or future-session storage.

A bug-ready input includes expected/actual behavior and impact, reproduction/environment and observed results/intermittency, established cause and affected sources, bounded fix/exclusions/dependencies/risks, acceptance/regression checks, method recommendation and temporary-probe disposition. Reuse complete current evidence without automatically invoking Analyze or investigation. Compare deciding inputs on receipt/resume; invalidate only dependent findings when scope is clear, otherwise mark relevant evidence stale. Missing cause or unconfirmed symptom returns an investigation-only draft/gap, not a ready fix ticket. With exact publication approval, that draft may be persisted as explicitly investigation-only work: retain attempted observations, missing cause/confirmation, the blocker and bounded diagnostic acceptance/next action; do not invent fix scope or assign implementation readiness. A standalone bug needs no artificial spec parent or implementation-step role: use the target's approved standalone classification. Match existing tickets before proposing a new one.

Discover companions under project guidance; inspect complete entries/relevant references for semantic compatibility and source identity. Missing/ambiguous capability blocks only its route. Native tracker work uses the maintained procedure in step 1, never prose substitutes or inferred persistence.

For material technical gaps, use compatible Analyze directly within existing inspection authority, supplying only missing questions and current evidence. Inspect its support and resume ticketing without making the user coordinate the handoff or approve routine inspection again. The agent resolves routine choices; return consequential uncertainty or unavailable authority/capability to its owner with a recommendation. For separately authorized delegation, discover Work On's conditional coordination library, not its delivery entry or old universal contract. Require root-owned allocation, finite bounds, protected ownership and inspectable returns; workers never recursively delegate. Missing compatibility blocks delegation, not equivalent direct work. Preserve active/uncertain state and spent allowances.

Read [validation](references/validation.md) when changing or testing this package.

## 1. Establish the agreement and tracker capability

Pin supplied agreement/technical readiness or bug evidence, deciding inputs (including dirty content), acceptance, exclusions, decisions, authority and protected work. Distinguish complete ready evidence from an explicitly unresolved investigation draft; the latter can authorize diagnostic work only, with its missing facts and bounded diagnostic acceptance preserved. For a standalone bug, checkable regression criteria can supply acceptance references without an owning spec. The ticketing caller owns routine design, dependency, method and verification choices from inspected evidence unless the user requests technical collaboration. These choices must preserve agreed behavior; they cannot silently add product commitments. Missing consequential product decisions return to their agreement owner as concise outcome/scope/risk questions with a recommendation; ticketing does not settle them by creating tasks. For a small cohesive change, avoid manufacturing a hierarchy; a direct-build recommendation does not replace an explicit ticket-creation request. Reuse suitable existing tickets rather than decomposing again.

Read the target's tracker, title, label, readiness and completion policies. Resolve its actual host/repository/project identity and available native parent and blocker capabilities through authorized read-only access. Discover the maintained tracker procedure through the companion discovery gate above, recording its source/revision and compatibility.

For GitHub, discover the actual `setup-project` package root through runtime/project metadata and read its complete `references/native-tracker.md` library entry directly, not the setup entry or label audit. Record source identity and check its discovery/authority, role/readiness and native-graph contract; missing/older incompatible libraries block this route without installation. Read the optional helper and its documented limits before choosing it. This reads a procedure library; it does not invoke `/setup-project`, authorize setup mutations or require a sibling installation. That procedure owns the graph algorithm/API recipes; use it throughout inspection, application and verification instead of copying it here. Other trackers need an inspected project-approved native procedure. Missing/incompatible required capability blocks remote graph work; ask for agreement on an explicit alternative, never silently substitute body links. Planning may continue without claiming persistence.

**Complete when:** agreement and technical readiness are pinned, decomposition is justified, target mappings and a compatible native procedure are known, or the affected capability gap has an owner and next action.

## 2. Inspect and propose cohesive tickets

Use the maintained procedure to inspect current issues and both directions of parentage and blockers, including all pages, database IDs, repository identities, transitive blockers and parent ancestry. Failed/incomplete reads are unknown, not absent edges. Include existing edges reachable beyond the proposed ticket set; unrelated ownership and blockers remain protected. Record the observed graph and observation time before proposing a delta.

Choose session-sized deliverables by behavior and ownership, not module count or a fixed ticket quota. Keep tightly coupled state/interface changes with one owner when splitting would reduce coherence. Separate design or validation when it is genuinely a bounded deliverable. Name true prerequisites rather than imposing a linear sequence for convenience; distinguish a scheduling blocker from shared ownership that should serialize or stay together. Dependencies do not grant delegation or dispatch authority.

Each proposed ticket contains:

| Item | Required content |
| --- | --- |
| Identity | Stable draft key or existing actual tracker identity, descriptive title under target convention, owning spec/revision or explicit standalone investigation identity |
| Behavior | One bounded intended outcome, rationale and referenced agreement/regression acceptance IDs; checkable ticket acceptance criteria |
| Scope | Owned behavior/files/interfaces where known, protected work and explicit exclusions; one cohesive session boundary |
| Verification | Appropriate existing/needed checks, environment and meaningful expected results; planned checks remain distinct from executed evidence |
| Dependencies | True blockers and why they precede this work; separately identify native owning parent and any coordination/ownership constraints |
| Classification | Mapped work-ticket role and independently justified other labels/readiness; no copied parent label set |

Apply the target's approved work-ticket role (for example, `implementation-step`, or its approved equivalent) to bounded work under a spec, including design and validation. A parent spec or subordinate spec retains the spec role; a delivery PR is not a work ticket. If an existing item has a conflicting workflow role, propose the exact authorized role correction rather than adding both. Assess ordinary type/readiness labels independently for each item's defined next action. During authorized publication, apply the target's mapped agent-ready label when criteria are actionable, consequential decisions settled, dependencies known and the next action agent-suitable; apply the mapped human-ready label when that action requires a human decision or capability. Native blockage alone must neither suppress readiness nor select human readiness: equivalent blocked and unblocked work receives the same classification, with blocker edges preserved. Record the evidence and justified assignment in the scoped publication delta. Reuse task/project authority for routine classification without redundant confirmation; missing assignment authority blocks that effect. Missing material evidence stays explicit, not fabricated readiness. Readiness never grants dispatch authority, proves eligibility or accepted integration, or bypasses native blocker/completion checks. Missing mappings/labels require a scoped decision, not an unrelated label/settings audit or automatic vocabulary creation.

**Complete when:** every proposed ticket has behavior, acceptance traceability, verification, exclusions and justified prerequisites; cohesive ownership is preserved; the native observation is complete enough to assess the proposed graph.

## 3. Resolve selected publication and exact graph authority

The agent owns decomposition and full ticket wording within the agreed outcome. In a configured project, requested ticket creation selects actual publication under the project's authority; do not ask the user to approve routine wording or paste full bodies for a second product review. Full ticket text belongs in the tracker. Draft/local/review-only requests select zero writes. Missing access or artifact authority is a specific blocker, not another plan interview or an implementation request.

Identify the intended delta with stable draft keys/reused IDs, titles/bodies, role/label deltas, parent → child membership and **dependent is blocked by prerequisite** edges with reasons. Keep complete wording available for fidelity/read-back without requiring conversational presentation. Distinguish existing edges, additions and protected unrelated state. Use the maintained procedure's combined existing-plus-planned conflict checks. Unknown graph reads, self-links, cycles, reversed blockers or conflicting parents block affected writes; do not remove/reparent unrelated work.

Reuse exact authority already supplied by the task/project for scoped creation/update, mapped roles and relationship effects. Where a consequential scope, ownership, relationship or permission decision is not covered, request approval of that exact delta with a concise outcome/effects summary and recommendation. Make the relationship/label plan identifiable and available; this gate approves effects, not line-by-line ticket prose. ADR changes retain explicit agreement/permission. Broad delivery permission, readiness or prose mentions alone are insufficient relationship authority. For new tickets, stable approved draft keys can identify the exact graph before database IDs exist. Create only the approved drafts, resolve the returned actual identities/IDs, then bind those keys to the IDs without changing the approved graph. If resolution is ambiguous, the observed graph changed materially, or the intended ownership/dependency changed, stop for reconciliation and renewed approval of the changed delta.

**Complete when:** the selected publication and exact graph/label effects have authority with protected state and draft-to-ID binding rules, or a draft/blocked return names the specific missing decision. No duplicate approval of unchanged commitments or routine wording is required.

## 4. Apply and read back the approved delta

Reinspect affected state against the approval immediately before writes. Publish/update only approved tickets and mapped role/other-label deltas, preserving unrelated content and assignments. Resolve actual repository identities and database IDs for new tickets; record draft-key bindings and per-operation outcomes. Read back titles, scoped body changes and actual role/readiness assignments against the justified delta; failed or mismatched label read-back remains partial/unknown, not verified readiness. Confirm each bounded work ticket under a spec has the approved role and no conflicting spec role, and each standalone bug retains its approved standalone classification.

Apply graph additions through the maintained native procedure. Use its helper only for compatible additive blockers in one github.com repository, with the exact approved plan and fresh inspection. Parentage and unsupported graph scopes remain with the procedure, not the helper. Keep server conflict protection enabled. Existing intended edges are no-ops; preserve unrelated edges and parentage. Removals or reparenting are separate specifically approved changes outside this additive route.

After writes, compare the persisted graph to the approved intended graph by actual identities/IDs, reading both directions and all pages via that procedure. Confirm intended parent membership, blocker direction, preserved unrelated state and conflict-free combined graphs. Verify labels separately; prose summaries can now reflect the observed native graph, but are never persistence evidence.

On timeout, interrupted creation, failed write or read-back, stop affected operations and retain successful, failed and unknown outcomes. Inspect actual issues/assignments/relationships before any retry; search for a possibly created ticket using approved content and identity evidence rather than creating duplicates. Ambiguous matches require clarification. Resume only missing approved operations after fresh inspection and authority checks; do not automatically roll back, delete, or replay the batch. A missing permission/capability or incomplete read-back blocks graph-dependent scheduling and requires a concrete next action or approved alternative.

**Complete when:** publication, mapped roles and both native relationship directions match the intended IDs with preserved unrelated state, or the return explicitly identifies partial/unknown outcomes and affected blockers. A clean rerun adds nothing.

## 5. Return concise ticket links or the affected blocker

After verified publication, lead with a table of linked ticket numbers/IDs and short descriptions, not full bodies. Separate failed/unpublished items and material blockers/decisions; never invent IDs for uncreated items. Plan-only output labels draft keys as drafts rather than tracker identities.

Keep ticket bindings/revisions, acceptance references, intended/observed/persisted graph and exact effect authority inspectable with procedure source and raw read-back. Report role/readiness separately, actual versus planned checks, partial/unknown effects, preserved state and documentation disposition under project evidence guidance. Native relationships remain authoritative; update summaries only within authority.

Inspect actual ticket contents, roles and graph against the intended delta. A verified graph proves neither blocker completion nor launch authority. Stop here; a caller resumes only its already-authorized responsibility.

**Ticketing completion:** cohesive tickets with approved, read-back native parentage/blockers and mapped roles, or an explicit plan-only/partial/blocked result with preserved state and next action. This is not implementation, accepted delivery, issue closure, merge or release.
