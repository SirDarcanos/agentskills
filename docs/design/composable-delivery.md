## Ownership and standalone boundaries

Each package has its own complete `SKILL.md`, conditional shipped references, invocation/authority/dependency gates, and checkable complete/partial/blocked returns. Calling a specialist uses its procedure in the current context unless separately authorized delegation is useful. Loading a skill grants no effects. Standalone completion stops at the row's output; it does not automatically advance the delivery pipeline.

All rows consume the minimal envelope below. Ordinary user requests supply the same facts through request/context inspection, not a mandatory form or new orchestration service.

| Owner and trigger | Additional inputs and procedure | Complete output and stop boundary | Conditional dependency / blocking outcome |
| --- | --- | --- | --- |
| `setup-project`: explicit setup/reconciliation | Existing context, workflow, model policy and approved operating delta | Approved operating docs and pointers, per-operation read-back; no application or backlog work | Existing domain/GitHub companions retain their gates; missing approval returns plan, unavailable required companion blocks its route |
| `shape-work`: unresolved idea/goals/priorities | Users, workflows, constraints, success, consequential trade-offs; owns discovery rounds and four concern dispositions | Agreed discovery brief, required/deferred/excluded/accepted-limitation record, decisions and gaps; no automatic spec publication | Uses `analyze`, `research`, `domain-modeling` only for relevant gaps; unresolved consequential intent blocks agreement |
| `write-spec`: express agreed behavior | Confirmed discovery/analysis, rationale, accepted limitations, acceptance IDs | Approved spec or labeled draft; optional specifically authorized spec publication and role/readiness read-back; no tickets/build | Maintained tracker library for publication; missing behavior approval leaves draft, missing native capability blocks publication |
| `write-tickets`: decomposition or publish ready investigation | Spec/technical readiness, or complete bounded bug evidence, current graph and exact approved delta | Cohesive tickets and verified native parent/blocker/role outcomes; or honest plan/partial result; no scheduling | Tracker library in discovered `setup-project`; missing native capability blocks persistence, not drafting; no prose substitute without agreement |
| `research`: bounded source question | Question, source/version scope, prior findings, output/retention authority | Cited findings, dates/versions, gaps/options and requested recommendation; no automatic implementation | Authorized source access; optional authorized background worker, otherwise direct research; required inaccessible source remains a gap |

| `domain-modeling`: changed meanings or qualifying decision | Exact subject, document mapping, source evidence, plan-only/approved mode | Existing companion's bounded planned/applied records and preserved history; no application edits | Retains its own authority and decision-record qualification; reading definitions needs no run |
| `investigate-bug`: reported defect lacking ready evidence | Expected/actual behavior, environment, reproduction, candidate matching tickets | Complete implementation-ready ticket via `write-tickets`, or duplicate reconciliation / investigation-only blocker; no shipped fix | `analyze`/`research` for gaps, `write-tickets` for publication; unconfirmed symptom or insufficient cause stays investigation work |

| `work-on-spec`: authorized spec delivery | Approved spec/tickets, native graph, prerequisite accepted integration and ownership | Ticket scheduling, inspected serial integration, cross-ticket verification/review/repair/recovery and overall report | `work-on` ticket agents and authorized bounded runtime required; unavailable delegation blocks multi-ticket execution, not graph inspection |
| `review-delivery`: explicit review or acceptance handoff | Full pinned dirty scope, standards/agreement and raw checks, independence authority | Separate independent Standards/Spec findings with freshness/limitations; no repairs or acceptance | Two read-only contexts separate from authors/each other's conclusions; unavailable independence blocks acceptance, self-inspection remains labeled separately |
| `pr`: report or authorized PR action | Actual delivered evidence, counting baseline, target branch and PR policy | Plain-language decision report and, if authorized, opened/updated PR with read-back; no merge/close/deploy/release | Git/host access for publication; missing evidence stays unknown and material acceptance gaps stay blocked |
| Each maintained `ask-*`: explicit assessment or policy-authorized handoff | Bounded question/criteria, neutral current evidence, named model authority and budget reservation | Validated advisory decision or no-call/unavailable/insufficient-data outcome; no engineering or policy mutation | Named transport/model and disclosure permission; absent/denied/exhausted authority yields zero automatic calls |

### Method contracts and composition

Recommend retaining the initial names: they describe distinct methods, align with the approved ticket plan, and avoid another naming migration. These four names were settled by #50 acceptance; `tdd` was already confirmed. Every method is independently usable, consumes a bounded ready scope, owns only its loop, and returns current local evidence plus partial/blocking conditions. None opens a PR or performs delivery acceptance by itself.

| Method | Owns / complete result | Block or limitation |
| --- | --- | --- |
| `tdd` | One behavioral increment: meaningful red → minimal green → refactor with checks green; repeat within scope; return observed failures, passes and refactoring evidence | Wrong-reason red is not sensitivity; unavailable required test/check blocks claim; technical lead selects seams without obligatory maintainer questionnaire |
| `prototype` | Bounded design/UX/feasibility experiment, runnable artifact, observations, decision/gaps and explicit artifact disposition | Stop when question answered or experiment bound reached; prototype is not production-ready; promotion needs new production scope/checks, retention/deletion/commits follow authority |
| `characterize` | Capture relevant existing behavior before safe change; distinguish intended invariants from known defects; return checks, observations and follow-on scope | Unknown intent remains unknown; passing characterization does not bless a bug or prove new acceptance |
| `acceptance-first` | Observable executable acceptance examples first, then increments implementing and checking the agreed workflow | Missing approved outcome/environment blocks affected example; examples are not a substitute for failure-path/integration coverage |
| `build-and-check` | Small implementation-first increment → immediate relevant check/inspection → inspect result before next increment | No accumulated unchecked increments; failed/material unrun checks stop affected progress; documentation/configuration may use non-unit checks |

Composition is sequential under one owner and ledger: e.g. prototype answers an interface question, `analyze` updates only affected readiness, then TDD implements the production scope; characterize protects observed invariants before TDD changes intended behavior. Methods return rather than recursively launch the next method. `work-on` decides the sequence, avoids duplicate checks when evidence is equivalent, and remains accountable for delivery gates. Standalone callers get the same limits/authority checks without being forced to invoke `work-on`.

## Minimal handoff and reusable evidence

Use compact Markdown in the target's existing approved task/PR location; a small direct run can keep it in the conversation. Multi-session work needs an approved durable pointer. No new schema service, versioning system, state directory, or manifest runtime is proposed.

Every handoff includes these five groups; inapplicable facts may be marked explicitly:

1. **Agreement:** target, bounded purpose, authoritative agreement revision/body digest and acceptance IDs, exclusions and confirmed decisions.
2. **Evidence:** deciding sources/revisions or content digests including dirty files, actual check/inspection results and environment, gaps/assumptions, relevant policy/domain pointers.
3. **Authority:** plan-only/inspection or exact approved effects with approval source; disclosure, delegation and installation remain separate. Unknown permission is ungranted.
4. **Ownership/state:** owned behavior/files/interfaces, protected work, branch/base/target and dependency evidence, prior findings/checkpoints and root execution-ledger pointer.
5. **Expected return:** artifacts/decisions/checks, completion/blocking conditions; worker identity, isolation and finite lifecycle bound only when delegated.

Return actual complete/partial/blocked outcomes, artifact/state pointers, criterion/risk evidence, failed/not-run/stale results, findings/lineage, ledger use, documentation disposition and next action. A named helper or worker's success label is not proof. Receivers inspect actual artifacts and raw evidence, not just summaries.

### Freshness rules

Evidence is current relative to deciding inputs, not a fixed number of hours. Record agreement and deciding code/caller/config/test/environment revisions plus measurement time where relevant. A bug-ready ticket includes expected/actual behavior and impact, reproduction and observed results/intermittency, established cause with affected sources, bounded fix/exclusions/dependencies/risks, acceptance/regression strategy and method recommendation. Temporary probes and instrumentation have recorded disposition; useful reproduction evidence survives without an unauthorized product fix.

On receipt and resume, compare relevant input identities and inspect source coverage. Reuse complete current investigation/analysis directly: do not call `analyze`, `investigate-bug`, research or a model merely because another phase starts. Missing data causes the smallest targeted investigation. Changed deciding code, agreement, callers, environment, contradictory evidence or newly relevant paths invalidate only dependent findings/checks; if impact cannot be isolated, mark all relevant evidence stale. Keep old evidence for its old state.

HEAD alone does not identify dirty work. Pin committed/staged/unstaged/included untracked changes, modes/symlinks/deletions/renames, exclusions and supporting inputs using the review owner's scope contract. Freeze scoped writes/integration or use an authorized immutable snapshot; compare discovery/fingerprints before and after checks/review. Record content-equivalent commits explicitly; integration/state-sensitive checks rerun. Significant repairs renew affected independent review; narrowly non-significant changes require documented impact analysis to retain evidence.

A duplicate bug uses the matching issue under authorized reconciliation, without a fake new hierarchy. Unconfirmed bugs or unresolved causes return attempted checks and investigation-only work, not a ready fix ticket. A later authorized fix consumes the ready ticket. Investigation-only invocation ends there.

## Companion compatibility and invocation

Discover by target/runtime catalog or explicit approved package location, not sibling paths. Read the complete candidate entry and relevant references; record resolved source/revision or digest. Check semantic capabilities, not a name or version string. With ambiguous candidates, request disambiguation before invoking the affected procedure. Recheck after source, authority or task changes. Each package ships its internal links; separately installed companions are named in prose and resolved through discovery.

The delivery execution contract is also a read-only library in discovered `work-on`: specialists/methods/review and `work-on-spec` can consume its envelope and ledger rules without invoking delivery or its explicit entry gate. Standalone callers act as their own bounded root for authorized delegated/corrective work; they discover that contract before such work, and report the dependent route unavailable if it is missing/incompatible. Plain inspection or a method's ordinary development loop does not require launching a delivery lead. This preserves one authoritative home for shared limits without forcing the entire workflow.

Required helpers block dependent responsibilities when absent/incompatible. Optional research/delegation/model routes may fall back to ordinary direct engineering only where genuinely equivalent and permitted. Required independent review, native persistence, domain decisions and material checks cannot be replaced by lead opinion. Planning or implemented-but-unaccepted returns remain useful. Installation/replacement is never the missing-helper fallback.

Accepted invocation gates: specialists and methods route both ordinary matching user requests and bounded authorized handoffs; no command-only frontmatter gate that conflicts with composition. `setup-project` retains explicit setup approval. Narrowed `work-on` accepts explicit user delivery and a bounded authorized lead/investigation-and-fix assignment; `work-on-spec` requires a request for overall delivery. Mere discovery or an investigation-only request cannot authorize a fix. #67 must reconcile the current `disable-model-invocation` and body gate together so #68 assignments work without pretending a generated command is user consent. `ask-*` invocation has the separate contract below.

## One execution and repair ledger

**Concurrency revision approved in [#130](https://github.com/SirDarcanos/agentskills/issues/130):** the former two-worker ceiling is superseded by [lead-chosen concurrency](../../workflow/work-on/references/contracts.md#lead-chosen-concurrency). The root chooses and adjusts useful concurrency with rolling scheduling, respecting actual resources, explicit restrictions and exclusive ownership. Submitted unfinished assignments remain tracked; ticket leads still request workers from the root, not a new pool. Existing consumer working agreements require exact reconciliation approval; the revision changes no repair/model budgets or package ownership. Earlier paper checks and execution records retain their original assumptions and results.

The root lead alone launches delegated tasks, reserves exclusive ownership and finite runtime bounds before launch, inspects returns, and integrates serially. Ticket agents execute methods/specialists in their own context; they request additional work/review from the root instead of spawning workers. Independent review contexts remain separate from authors and each other's conclusions, sequential when only one slot is free. If the runtime cannot provide bounded lifecycle and inspectable results, delegation is unavailable. Unknown worker state retains its slot and ownership until confirmed stopped or safely isolated. Stable shared interfaces and isolation are required for concurrent writers; shared edits serialize.

The ledger minimally records run ID, authority and permitted effects, active worker/owner/bound/status, reserved scopes/interfaces, agreement/state pointers, checkpoint/finding lineage and spent repair cycles, plus any model-call reservations/usage. Resume reconciles actual artifacts, workers, graph and uncertain remote operations before writing or retrying. Store under target retention/disclosure policy, not automatically in a public repository.

Retain **two automatic repair cycles per work-unit acceptance checkpoint**, including the final integrated checkpoint. First corrective assignment/direct fix starts a cycle; partial/failed attempts spend it. Diagnosis is bounded but not itself a correction cycle. Ordinary planned red–green increments are method development, not failed acceptance repair episodes; a corrective attempt on a recorded finding is counted regardless of method used. Related regressions and renamed/moved findings retain lineage and spent count. A child finding moved to integration gets no fresh allowance; genuinely new cross-ticket findings use the integrated checkpoint. Closure requires current evidence resolving all material findings; recurrence of the same unresolved cause does not start a new budget.

At exhaustion, substantive disagreement, unsafe authority, or known missing capability: stop affected execution, retain partial work/evidence and recommend bounded design/scope/environment reassessment. Further repair needs an explicitly approved revised plan/budget. A new session, worker, specialist or ticket cannot reset counts. Scope/acceptance changes require their proper owner and authoritative record updates.

Single-change lead owns its preflight, local/integrated verification, review disposition, repairs and recovery. Overall lead owns cross-ticket decisions, frontier, serial integration, whole-spec checks, review and integrated repairs/recovery. Both report implemented, verified, unverified, deferred and blocked work and distinct build/accept/report gates. Child integration, ready labels and issue closure do not prove overall readiness. Accepted/merged/deployed/released and installed migration are separate states under target policy.

## Model-use permission contract

This is a design for #51–#53, **not an opt-in for this repository**. `setup-project` owns establishing/reconciling an approved policy, default home `docs/agents/model-use.md`, linked from the target's `AGENTS.md`. Preserve an existing authoritative equivalent and rationale/provenance; propose only changed facts. Reruns do not broaden permission or perform incidental service operations.

The policy identifies none/allowed use; exact skill, variant/model/service/endpoint; purposes; data/disclosure boundaries; call/retry/spending limits and budget scope; delegation allocation; service start/stop ownership; fallback/substitution permissions; escalation and approval provenance. Missing material limits are ambiguous, not unlimited. Availability, credentials and a preference are not authorization. Setup proposes and obtains approval before writing/reconciling policy; no downloads, installs, credentials, service starts or calls happen as setup side effects.

Two independent checks apply: lead verifies the proposed consultation fits policy/authority and reserves budget; the assessment owner rechecks permission, neutral payload, transport, limits and response validity immediately before sending. Assessment packages own named-provider enforcement and interpretation, not a second project policy or mandatory wrapper. Leads retain accountability for engineering decisions.

| Invocation | Authority and outcome |
| --- | --- |
| Autonomous optional consultation | Requires unambiguous approved policy for the exact skill/model/purpose/data/endpoint and remaining shared limits. Authorized calls need no repeated confirmation. Absent, none, denied, conflicting or exhausted permission makes zero calls; delivery proceeds with ordinary engineering where sufficient, or reports a material evidence gap |
| Explicit user assessment | Authorizes that named bounded assessment under its normal package call/disclosure budget and applicable restrictions, including Jev's normal billable scope. Does not override an explicit project prohibition; resolve conflict with the authorized policy owner. No permission for other services, expanded private disclosure or installations |
| Unavailable/invalid response | Autonomous delivery uses policy-authorized direct assessment if allowed, otherwise records model unavailable and continues ordinary judgment without attributing a model result. Explicit assessment retains offer-and-wait direct fallback unless the user already authorized it |
| Substitution | Only an explicitly approved named alternative with compatible purpose/data authority and remaining limits; default is none. The lead invokes the alternative's distinct package; the original named assessment never changes its model/transport. Recheck the alternative before sending; local permission never implies hosted disclosure |
| Valid insufficient-data | Preserve gap and bounded next evidence action; not a service failure or excuse to ask another model until green |

Change `ask-clef`, `ask-clef-flash`, `ask-nimble`, and `ask-jev` frontmatter, body gates, API/lifecycle/fallback references, completion criteria and offline checks together. Each remains separately identifiable; no model ensemble is required. Suitability still precedes service operations; deterministic questions use code/facts, open-ended research uses normal investigation. Model output remains advisory and cannot substitute for checks or independent Standards/Spec review.

Call budget accounting is part of the root ledger, not a new gateway: reserve before sending, record actual attempted requests (including transport retries, correction calls, failures with unknown charge), reconcile usage, and never replenish on child handoff/resume. Question batches do not evade request/spend limits. Keep existing package request/correction ceilings as additional upper bounds; use the stricter policy/package allowance. At most one evidence-corrected request per assessment remains; malformed/transient responses use only the named API's bounded retry rules and available shared allowance. Unknown cost is not zero: if a safe allowed reservation cannot be established, block paid send. Workers ask the root for a bounded model allocation, cannot gain authority by spawning another caller, and never auto-launch model panels.

Service lifecycle: reused services stay untouched. Startup needs explicit policy or invocation-specific startup authority for the exact service; installs/downloads remain separate. Record owned process handle; follow approved shutdown disposition, otherwise ask. No endpoint/model substitution to avoid startup denial. No retained private regression records without retention authority.

### Installed-copy transaction and rollback boundaries

#69/#74 own a local, private migration record: inventory runtime roots, actual copies/aliases/registrations/install mechanism, symlinks/shared targets, local modifications and source/version; exact old→new mapping and approvals; full-package byte/mode/link checksums and backup locations; replacement/companion source and validation; per-operation states and restore instructions. Candidate names are observations, not approved removal targets (see inventory).

Before removal/overwrite, verify complete backups (including shipped references/scripts/assets, modifications and registration/link metadata) outside all active discovery roots and outside this public repository. For symlinks, retain link metadata and the authorized source contents needed for restore; removing a link must not delete shared source. Stage the coherent replacement set, verify backups and exercise restore in an isolated location. Invalid backup or incomplete replacement blocks retirement with old installation intact.

Apply only the approved active-copy/link/alias/registration changes, preserving independently required companions and unrelated roots. Activate replacement, refresh supported runtime discovery, then inspect actual resolved sources/internal links/companions and absence of competing retired implementations; same-name replacements must resolve to new source, not just show the same name. Keep verified backups.

Use inspectable states (inventoried → approved → backed-up/restore-tested → staged/validated → retired/activated → discovery-verified, or rollback-needed/restored/blocked). Journal intent and actual outcome around each effect. On interruption, inspect real source/discovery/registration/checksums against the record before retry; do not back up a replacement as though it were the old copy or blindly replay removal. Unknown operations block dependent destructive actions.

Activation failure uses the approved rollback scope: deactivate only replacement registrations/copies this transaction owns, restore complete backed-up files/links/registrations, refresh discovery and verify old behavior/source resolution. Protect intervening unrelated changes; conflicts return incomplete recovery rather than overwrite. If rollback itself fails, retain artifacts and exact remaining state. Report backed-up/replaced/retired/preserved/verified items and recovery instructions locally.

Reverting design/source commits affects repository documentation/code only. It neither restores installed copies, tracker state, model permission, nor downstream data. Before installed activation, rollback means retaining the working old installation and staged/backup artifacts. After activation, full local restore/read-back is required; old broad `work-on` needs its matching old companions, not an incompatible mixture. Source rollback of extracted packages must restore caller dependencies atomically or explicitly block the affected route. No approved-target retirement erases historical source or backup.
