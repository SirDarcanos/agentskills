# Specification publication

Read completely when tracker specification publication or reconciliation is requested. This procedure owns publication intent, fidelity and role/readiness outcomes, not the tracker's native graph algorithm.

## 1. Inspect destination and exact authority

Read target tracker/title/label policies and live mappings; verify read access, inspect existing spec identity and search relevant open/closed matches before creating. A failed search is unknown, not proof of absence. Reuse the matching authoritative spec; ambiguous matches require disambiguation. Confirm exact create/update/content/label authority and approved body or authoritative-home pointer. Credentials and approval of behavior confer no remote write permission.

For GitHub, discover compatible `setup-project`, read its complete entry and maintained `references/issue-tracker.md` as a read-only library without invoking setup. It must support approved mapped spec/work-ticket roles, separate readiness, preserved unrelated state and native identity/pagination/read-back for any affected relationships. Other trackers need a project-approved native procedure. Missing permissions, mappings or required native capabilities block persistence, not drafting. Use the library if inspecting affected native graphs; preserve existing relationships and create no children or blockers as part of spec writing. No prose substitute for an unavailable requested native feature without explicit agreement.

**Done:** destination/existing identity, title and role mappings, deciding evidence and exact approved delta are known.

## 2. Publish the authorized delta

1. Follow the target's title convention; classify by purpose and mapped metadata, never title parsing.
2. Apply the mapped **specification role**, not the mapped **implementation-step role**. They are mutually exclusive. A conflicting role needs exact removal authority before correction. Preserve unrelated labels and relationships; assess other classifications independently. Creating/changing the label vocabulary requires separate approval.
3. Assess readiness independently: approved behavior plus resolved material shared design decisions can be actionable under target policy; a draft or unresolved design cannot. Missing technical evidence remains a gap rather than guessed readiness. Parent readiness permits coordination of eligible children, not duplicate implementation or bypassing native blockers/completion evidence.
4. Apply only authorized readiness additions/removals. If a stale ready assignment cannot be corrected, report the contradiction and block reliance on it; publication and labels do not approve commitments.
5. Write only the exact approved content/role/readiness delta. For an existing issue, preserve history and unrelated body sections. Publication of a labeled draft is valid when specifically authorized; it stays draft and unready.

**Done:** each attempted effect and known/unknown result is recorded; no decomposition or implementation has begun.

## 3. Read back and compare

Read persisted identity, title, body/agreement pointer and revision, mapped spec role, absence of work-ticket role, independently assessed classifications/readiness and preservation of unrelated state. Compare actual values with the approved delta, not only command exit status.

After timeout or partial failure, inspect actual state before retrying. Never blindly recreate: uncertain identity could already exist. Failed reads or mismatches remain partial/unknown publication; report successful effects separately from failed/uncertain ones. Corrective operations need their own authority if outside the approved delta.

**Done:** matching read-back establishes publication; any unknown/mismatch is an explicit blocker. Return publication and readiness separately to the entry point, including evidence, operation states and smallest next action. Stop before ticket creation.
